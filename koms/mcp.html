Turn on MCP in Home Assistant

The Model Context Protocol is a standard way for an AI app to use a piece of software: ask it questions, call its functions. Home Assistant can be that server, which turns "turn the kitchen light off" into something Claude or ChatGPT can actually do.

Nothing needs to be installed. Home Assistant has had an MCP server built in since 2025.2; you switch it on, copy a URL, and paste that URL into your AI app. The whole thing takes about two minutes.

1 · Switch the server on

  1. Open Settings → System → AI

    On the Model Context Protocol card, press Enable. If the card already shows copy buttons next to its URLs, it is on and you can skip to the next step.

  2. If you don't see that card

    Add the integration by hand instead: Settings → Devices & services → Add Integration → Model Context Protocol Server, then follow the prompts. Same thing, older route.

  3. Copy the URL

    There are two kinds of URL on that card. Your MCP API gives the AI everything Home Assistant itself can reach; the per-API URLs give it one specific assistant's abilities. Start with Your MCP API — the narrow ones are for when you want to limit a client on purpose.

    On your local network it looks like http://homeassistant.local:8123/api/mcp, or with the IP address instead of the name. Copy it exactly; a missing http or a stray trailing space is the most common reason the next step fails.

What the URL actually is

/api/mcp is the modern Streamable HTTP endpoint. Older guides and older tools use /mcp_server/sse, which still exists and still works, but is the legacy transport. If a client supports Streamable HTTP, give it /api/mcp.

2 · Decide what the AI may touch

This is the part worth slowing down for. The MCP server does not invent new permissions: a client can only see and control entities that are exposed to voice assistants. That list is shared with Assist, Google Assistant and Alexa.

Settings → Voice assistants → Expose. Each entity has an assistant checkbox, and there is a bulk Expose entities button. Start with a handful — a lamp, a thermometer, one switch — and add more once you have seen how the AI behaves.

3 · The login

You do not create a token and you do not paste a password. Home Assistant implements OAuth 2.0 with PKCE: your AI app opens a browser, you sign in to Home Assistant as usual, and the app receives its own credential. Home Assistant supports OAuth Client ID Metadata Documents, so a modern client fills in its client ID and callback URL without being asked.

  • There is no client secret. If a client insists on one, type anything; if it is optional, leave it empty.
  • A manual client ID must be the AI app's own address — https://claude.ai, https://chatgpt.com — never your Home Assistant URL. Home Assistant checks that the redirect URI belongs to the same domain, so your own URL fails the flow.
  • Cutting a client off is done by removing its refresh token in your profile, or by turning the integration off. Changing your Home Assistant password does not by itself revoke an app's access.
An AI with this access can open your garage door

It can do anything you can do with the entities you exposed — including locks, alarms and heating. Two habits make that safe rather than alarming: expose narrowly, and leave the "control Home Assistant" confirmation on in the client so it asks before acting. Claude and ChatGPT both ask by default; keep it that way.

4 · If the AI runs in the cloud, it needs a way in

This trips up more people than anything else on the page. Some clients run on your computer and can reach homeassistant.local directly — coding agents in a terminal, for example. Others run on the vendor's servers even when you use a desktop app: Claude and ChatGPT connect from the cloud, so your Home Assistant must be reachable from the internet.

  • Home Assistant Cloud (Nabu Casa) is the least fragile option: an HTTPS address like https://abcdef1234.ui.nabu.casa that already terminates TLS and keeps hostnames canonical. Use https://<your-id>.ui.nabu.casa/api/mcp.
  • Your own tunnel or reverse proxy works too, but the hostname must match what Home Assistant is configured to expect — Settings → System → Network, the internal and external URL. The OAuth discovery step is strict about this and fails with a confusing error when it does not match.
  • Local addresses will not work for cloud clients. homeassistant.local and 192.168.x.x are not reachable from someone else's data centre, and should not be.

What the AI gets, and what it doesn't

The server exposes tools (the actions the chosen assistant can perform), prompts (instructions telling the model how to call them), and one resource: a read-only snapshot at homeassistant://assist/context-snapshot, available when the assistant can report live context. That snapshot is handy for debugging what the model actually sees.

Not supported: sampling (the server asking the model to generate something) and notifications (the server pushing an event). So an AI can poll your house, but Home Assistant cannot tap it on the shoulder when the door opens. For that, use an automation that calls the AI, not the other way round.

The other direction: Home Assistant as a client

Home Assistant can also use MCP servers. Add Settings → Devices & services → Add Integration → Model Context Protocol and give it an SSE URL, plus a client ID and secret if the other server needs OAuth. Tools only — prompts, resources, sampling and notifications are not supported in that direction. To use the tools, point a conversation agent at that integration instead of at Assist; an agent takes one toolset, not both.

If the login keeps failing

OAuth fails, or loops

Check the client ID: it must be the AI app's base URL, not your Home Assistant address. Check that the URL you gave the client matches the internal or external URL configured in Settings → System → Network. And check ip_bans.yaml in your configuration folder — repeated failed logins can ban the client's address, which then looks like a broken login rather than a ban.

"Discovery failed" through a tunnel or proxy

Home Assistant builds the OAuth metadata from the hostname it is asked on. If your proxy does not forward the original host and scheme (X-Forwarded-Host, X-Forwarded-Proto), or if the external URL is set to something else, the metadata comes back with relative paths and strict clients reject it. Fix the external URL first, then the forwarded headers. Home Assistant Cloud avoids both problems.

A client cannot register itself

Home Assistant supports Client ID Metadata Documents, not the older RFC 7591 dynamic client registration. Clients that require 7591 have to be configured by hand, with the authorization and token endpoints typed in.
